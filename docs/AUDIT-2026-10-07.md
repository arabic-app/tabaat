# Audit Tabaat — 7 octobre 2026

## Conclusion

Tabaat peut rester un site statique léger. Les priorités sont la protection de l’administration, la conservation des modifications et la fiabilité de la publication. Une migration complète vers Next.js n’est pas nécessaire pour corriger les défauts identifiés.

Maktabati fournit des exemples utiles de stockage IndexedDB, de file de synchronisation, de recherche normalisée, de modales accessibles et de compression d’images. Ses implémentations doivent être adaptées et revues, plutôt que copiées telles quelles.

## Périmètre et méthode

Lecture du catalogue, du site public, de l’administration, du formulaire de propositions, du service worker et du Worker Telegram/chat/statistiques. Comparaison ciblée avec `/Users/hamdi/Desktop/maktaba_project/maktabati`.

Des reproductions locales utilisent le code existant dans des environnements Node isolés, avec réseau et stockage simulés. Aucun appel aux API d’écriture, aucun e-mail envoyé, aucune publication et aucune modification du code applicatif. Les scripts ajoutés sont des outils de diagnostic : ils démontrent certains comportements actuels, pas une suite de tests de conformité du futur correctif.

Limites : pas d’audit visuel sur navigateur, pas de mesure Lighthouse, pas de vérification des secrets/configurations déployés, des permissions GitHub ou du code Apps Script (absent du dépôt). Les risques dépendant de ces éléments sont explicitement conditionnels. Aucun audit complet de Maktabati.

## Correctifs prioritaires

### 1. P1 — HTML non assaini et gestion fragile des attributs

**Suivi :** correctif local implémenté après validation de la conception. Voir [CONTENT-SECURITY.md](CONTENT-SECURITY.md) et la suite `npm test`. Le diagnostic ci-dessous décrit l’état initial audité; les protections complémentaires CSP/CDN et le point 2 restent ouverts.

**Code :** `index.html:2051` (`bookCardHTML`), `index.html:2176` (`openNoteModal`), `admin/index.html:1679` (`cleanHtml`), `admin/index.html:2572`.

Les titres, auteurs, éditeurs et plusieurs URL sont interpolés dans du HTML. Les notes et corrections sont insérées via `innerHTML`. `cleanHtml` élimine seulement quelques contenus vides : ce n’est pas un assainissement.

**Reproduction :** un titre contenant `<img src=x onerror="alert(1)">` est conservé comme balise dans le HTML généré. Le script de diagnostic vérifie la chaîne produite sans exécuter la charge dans un navigateur. Un auteur `O'Neil` produit aussi un gestionnaire `cardAuthorSearch('O'Neil')` invalide : `encodeURIComponent` n’échappe pas l’apostrophe.

**Impact :** si du contenu malveillant atteint le catalogue, il peut exécuter du JavaScript sur le site. L’administration partage la même origine et stocke le PAT GitHub en localStorage : une injection sur le site public peut donc exposer ce PAT sur le navigateur d’un administrateur. Aucun vol ni contenu malveillant existant n’a été constaté.

**Correctif :** texte via `textContent`; événements via `addEventListener` et identifiants en `dataset`; validation des protocoles et chemins d’URL; assainissement avec liste autorisée du HTML riche au chargement et à l’enregistrement. En complément, politique CSP adaptée à l’hébergement et intégrité des scripts CDN. Le HTML riche de Maktabati utilise aussi `dangerouslySetInnerHTML` dans `TabaatBookCardModal.tsx` : ce n’est pas un exemple à recopier sans protection.

### 2. P1 — Authentification de l’admin entièrement côté navigateur

**Code :** `admin/index.html:1622`, `admin/index.html:1807`, `admin/index.html:1815`, `admin/index.html:2716`.

Le hash est inclus dans la page et le marqueur de session dérive de ce hash public. Le verrouillage repose sur localStorage. Ces mécanismes peuvent être contournés côté navigateur; `github_token_secured` contient le PAT en clair malgré son nom.

**Nuance :** contourner l’écran ne donne pas automatiquement un PAT GitHub. GitHub continue à contrôler les écritures. Le défaut concerne la fausse barrière d’accès et l’exposition d’un PAT déjà enregistré.

**Correctif :** API administrative authentifiée sur Worker ou serveur, session vérifiée côté serveur et jeton GitHub conservé côté serveur. Si l’architecture actuelle est maintenue temporairement : PAT finement limité au dépôt et aux permissions nécessaires, expiration courte, pas de stockage permanent par défaut. Une session frontend seule ne protège pas les actions Apps Script.

**Inspiration :** séparation client/serveur et validation de session de Maktabati; revoir les règles de rôles avant réutilisation.

### 3. P1 — Perte de modifications et suppression prématurée des suggestions

**Suivi :** correctif local implémenté après validation. Brouillons et mutations persistés, restauration au démarrage, verrou entre onglets et nettoyage des suggestions après confirmation GitHub. Voir [ADMIN-DRAFTS.md](ADMIN-DRAFTS.md) et `npm test`. Le diagnostic ci-dessous décrit l’état initial; les confirmations Apps Script du point 5 restent ouvertes.

**Code :** `admin/index.html:1639` (état), `admin/index.html:2596` (`saveBook`), `admin/index.html:2679`, `admin/index.html:3838`.

Les livres modifiés et les mutations à publier vivent uniquement en mémoire. L’avertissement `beforeunload` existe, mais ne restaure rien après fermeture, crash ou interruption mobile; il ne couvre pas non plus tous les champs de formulaire avant leur enregistrement.

Lorsqu’un livre vient d’une suggestion, celle-ci est supprimée dès l’enregistrement en mémoire, avant le succès GitHub. Une fermeture ou une publication échouée peut faire perdre à la fois le brouillon et la suggestion.

**Correctif :** persister brouillon, mutations et suggestion associée dans IndexedDB; restaurer au démarrage; supprimer ou marquer la suggestion traitée seulement après publication confirmée. Afficher trois états distincts : brouillon, enregistré sur cet appareil, publié.

**Inspiration :** `src/utils/idbStorage.ts`, `src/services/syncQueue.ts`, `src/components/common/SyncStatusBadge.tsx` de Maktabati. Adapter la file à GitHub et à la modération.

### 4. P1 — La fusion GitHub n’empêche pas les conflits de livre

**Code :** `admin/index.html:2599`, `admin/index.html:2774`, `admin/index.html:2785`.

La récupération du SHA puis les nouvelles tentatives sont utiles pour préserver les changements sur des livres différents. En revanche, les créations utilisent `max(id)+1` et les modifications remplacent tout le livre.

**Reproduction :** deux éditeurs créent chacun le livre 433 depuis le même catalogue. Après publication de B, la fusion de A remplace B : un seul livre reste. Deux modifications du même livre subissent également une règle implicite « dernier enregistrement gagnant », même si elles portent sur des champs différents.

**Correctif :** allocation des nouveaux identifiants par un backend sérialisé; conserver des identifiants numériques pour la compatibilité actuelle avec le bot et Maktabati. Stocker la version de base du livre, comparer base/local/distant et signaler les conflits avant de remplacer un livre modifié à distance. Si des UUID sont choisis à terme, prévoir une migration des consommateurs et des liens `?book=`.

### 5. P1 — Mauvaise gestion des propositions et confirmations opaques

**Code :** `feedback.html:1061`, `feedback.html:1095`, `admin/index.html:2894`, `admin/index.html:3123`, `admin/index.html:3219`.

Trois problèmes distincts :

- Le formulaire affiche le succès après un événement iframe, ou après six secondes, sans savoir si l’écriture a réussi. Suppression et réponse e-mail annoncent aussi un succès après un délai fixe.
- Les propositions sont identifiées par leur numéro de ligne. Si Apps Script supprime physiquement une ligne, les indices suivants deviennent périmés; une deuxième suppression peut viser une autre proposition. Le comportement du serveur reste à vérifier.
- Éditions et vérificateurs sont filtrés séparément avant concaténation avec `##`. Avec une deuxième édition sans vérificateur et une troisième renseignée, le vérificateur de la troisième se retrouve associé à la deuxième.

**Correctif :** API renvoyant un résultat JSON explicite et identifiant stable; opérations idempotentes; couples édition/vérificateur sérialisés ensemble; état « en attente » conservé jusqu’à confirmation.

**Point serveur à vérifier :** les actions `delete` et `replyEmail` ne transmettent aucun justificatif d’administration dans le code client. Le code Apps Script et ses permissions de déploiement sont absents : leur ouverture aux visiteurs ne peut pas être affirmée. Vérifier aussi la confidentialité des adresses e-mail puisque les propositions sont lues via l’export CSV de la feuille. Les permissions et l’identité d’exécution dépendent du déploiement [Apps Script](https://developers.google.com/apps-script/guides/web).

### 6. P1 — Cache hors ligne pouvant restituer une vieille version

**Suivi :** correctif local implémenté après validation. Clés canoniques, JSON validé, migration des dernières copies valides, erreur explicite sans données, état/date du catalogue et cache d’images borné. Voir [OFFLINE-CATALOGUE.md](OFFLINE-CATALOGUE.md) et `npm test`. Le diagnostic ci-dessous décrit l’état initial; `docs/audit/sw-checks.cjs` lance désormais les tests de régression du service worker.

**Code :** `index.html:1603`, `sw.js:87`, `sw.js:94`.

Chaque chargement ajoute `?_t=Date.now()` et stocke cette URL entière comme clé. Trois chargements donnent trois entrées différentes. La lecture hors ligne ignore la query et peut sélectionner la première version conservée plutôt que la dernière.

**Reproduction :** trois réponses simulées de versions 1, 2 et 3; le repli du service worker restitue la version 1. Sans cache, il renvoie HTTP 200 avec `[]` : le site présente une absence de résultats au lieu d’un problème de disponibilité.

**Correctif :** clé canonique unique pour chaque fichier de données; écriture du cache attachée à la durée de vie de l’événement; validation du JSON avant remplacement; erreur explicite quand aucune donnée n’est disponible; indicateur hors ligne et date du catalogue affiché. Retirer le cache-buster ou le réserver à une action de rafraîchissement volontaire.

**Autres points :** `activate` supprime tous les caches autres que `tabaat-v14` sans filtrer le préfixe; restreindre aux caches de Tabaat. Les pages admin sont préchargées mais ensuite servies uniquement par le réseau : supprimer cette précharge inutile. Borner aussi les images en cache et contrôler les origines/cache des appels externes.

### 7. P1 — Statistiques non fiables et dépendance du chat aux analytics

**Déploiement du 8 octobre 2026 :** Worker SQLite et admin GitHub Pages publiés après autorisation explicite. Les trois limites de couverture de la revue sont éliminées (pannes de lecture KV/cache, conservation J−34 et suppression J−35), avec vérification par mutations isolées. Suite locale : 75/75; copie de publication limitée au point 7 : 40/40. Import KV confirmé en production, avec les mêmes totaux avant/après sur les 30 jours UTC. Version Worker `d6196480-061b-414c-97eb-5bb68fe6cd07`; code et admin publiés dans le commit `cf324f3`. La collecte a été brièvement suspendue pendant la bascule; les événements reçus durant cette pause ne sont pas comptés.

**Suivi :** correctif local implémenté. Compteurs atomiques dans un Durable Object SQLite, import unique des agrégats KV, collecte chat indépendante avec erreurs absorbées, compteur `totalVisitors` raccordé dans l'admin et libellés sur 30 jours UTC. Le cache de lecture de 60 secondes reste secondaire. Voir [telegram-bot/README.md](../telegram-bot/README.md#statistiques-audit-point-7), `tests/analytics.test.cjs` et `tests/admin-stats.test.cjs`. Le diagnostic ci-dessous décrit l'état initial. Les tests couvrent également les pannes de lecture KV/cache et la frontière de rétention J−34/J−35. Le Worker et l'admin sont déployés et l'import en production est confirmé; l'anti-abus du point 8 reste ouvert.

**Code :** `telegram-bot/src/index.js:233`, `telegram-bot/src/index.js:196`, `admin/index.html:3278`.

Chaque événement fait une lecture puis une écriture du même agrégat quotidien. Deux événements simultanés peuvent lire la même valeur et se remplacer.

**Reproduction :** deux incréments simultanés donnent une vue au lieu de deux. Avec une réponse du chat présente en cache, une erreur d’écriture des statistiques entraîne HTTP 500 au lieu de transmettre cette réponse.

Cloudflare documente les écrasements possibles et la limite d’une écriture par seconde pour une même clé dans [Workers KV](https://developers.cloudflare.com/kv/api/write-key-value-pairs/).

L’admin renseigne le compteur de visiteurs uniques avec la somme des vues du graphique plutôt qu’avec `totalVisitors`. Les « totaux » renvoyés par le Worker correspondent à 30 jours; même `totalVisitors` serait une somme de visiteurs uniques quotidiens, pas des personnes distinctes sur 30 jours.

**Correctif :** compteurs sérialisés et regroupés, par exemple Durable Object; analytics en tâche indépendante avec erreur absorbée; libellés « vues sur 30 jours » et « somme des visiteurs quotidiens ». Corriger le branchement UI. Les statistiques ne doivent jamais faire échouer la fonction principale du chat.

### 8. P2 — Validation et protection incomplètes du Worker

**Code :** `telegram-bot/src/index.js:65`, `telegram-bot/src/index.js:175`, `telegram-bot/src/index.js:243`, `telegram-bot/src/index.js:270`, `telegram-bot/src/index.js:639`.

`{ "message": 123 }` provoque HTTP 500 au lieu de 400. Le webhook accepte les POST hors `/chat` et `/track` sur des chemins quelconques; son secret et celui de `/setup` ne sont exigés que s’ils sont configurés. `/stats` est ouvert quand `STATS_KEY` est absent. `/track` n’a pas de limite native et accepte des événements fournis librement, ce qui permet de polluer les compteurs et consommer des écritures.

**Correctif :** schéma d’entrée, borne du corps avant parsing, routes exactes et 404/405 explicites; configuration administrative requise en production et refus lorsque manquante; clé de statistiques dans un header plutôt que l’URL; anti-abus pour `/track`, quota global et surveillance des erreurs. CORS restreint aux origines prévues pour le widget, en complément des vrais contrôles d’abus : CORS seul ne bloque pas un client externe.

## Optimisations et améliorations

### 9. P2 — Unifier et indexer la recherche arabe

**Code :** `index.html:1592`, `index.html:1945`, `admin/index.html:1669`, `feedback.html:743`, `telegram-bot/src/index.js:334`.

Les quatre normalisations divergent. Sur le site, `ابن رجب` et `بن رجب` ne sont pas équivalents; `مصطفى` et `مصطفي` non plus. Le Worker normalise davantage de lettres mais n’utilise pas les mêmes règles. Les champs sont renormalisés à chaque frappe et toutes les cartes visibles sont reconstruites.

**Proposition :** fonction commune avec fixtures métier; retirer tatweel/diacritiques, normaliser espaces et variantes validées, gérer Ibn/Bin en mots entiers. Préparer un index normalisé une fois au chargement et appliquer un debounce court (150–200 ms). Conserver la pagination existante par lots de 20, déjà utile.

**Inspiration :** `src/utils/arabicUtils.ts`, ses tests et `src/hooks/useBookSearchAndFilters.ts`. En vanilla JS, reprendre les principes de calcul différé et de séparation de fonctions, pas les hooks React.

### 10. P2 — Réduire le poids des images et sécuriser l’upload

**Suivi du 8 octobre 2026 :** correctif local implémenté : validation du contenu et des limites, compression des nouvelles couvertures avec aperçu avant envoi, conservation des originaux joints et inventaire sans suppression. Voir [MEDIA-UPLOAD.md](MEDIA-UPLOAD.md) et [le rapport des médias](audit/media-inventory.json). Après contrôle indépendant et autorisation explicite, 222 médias non référencés (52,7 Mo) ont été supprimés localement; tous les médias du catalogue restent présents. Voir [la confirmation et le nettoyage](MEDIA-UNREFERENCED-CHECK.md). L’upload précède toujours la publication du livre. La validation visuelle sur navigateur/mobile reste à effectuer avant déploiement.

**Code :** `admin/index.html:2457`.

L’upload vérifie l’extension, sans compression ni limite de poids visible. Le chargement d’une couverture de plusieurs Mo peut être lent et remplir rapidement le cache mobile. Chaque fichier est ajouté à GitHub avant publication du livre, ce qui peut laisser des médias non référencés si le formulaire est abandonné.

**Proposition :** redimensionnement/compression avec objectif de lisibilité, aperçu, contrôle du type réel et taille maximale; conserver des originaux lorsqu’ils servent à lire des détails. Créer des variantes pour l’écran. Prévoir un inventaire des médias non référencés avant toute suppression. R2 est une option si le volume ou le workflow le justifie; ce n’est pas un prérequis aux premiers gains.

**Inspiration :** `src/utils/imageCompression.ts` (600 × 800, qualité 0,75 par défaut dans Maktabati), `src/services/r2StorageService.ts`. Adapter les dimensions aux couvertures et aux corrections de Tabaat plutôt que reprendre les valeurs sans contrôle visuel.

### 11. P2 — Distinguer erreur réseau et catalogue vide

**Code :** `index.html:1644`, `admin/index.html:3681`.

Le site se contente d’un avertissement console lorsque le chargement échoue. L’admin transforme une erreur réseau ou JSON en tableau vide et continue. Créer un livre dans cet état peut produire un identifiant déjà occupé puis l’écraser lors de la fusion.

**Proposition :** états loading/error/ready distincts, bouton Réessayer, cache de secours validé, actions de création désactivées tant qu’une base fiable n’est pas chargée. Valider le schéma du catalogue à la réception et avant publication.

### 12. P2 — Délais du chat et cache des réponses

**Code :** `index.html:2884`, `telegram-bot/src/index.js:152`, `telegram-bot/src/index.js:539`, `telegram-bot/src/index.js:561`.

Aucun délai d’abandon explicite n’est appliqué aux appels IA ni à la requête du widget. Une requête lente peut bloquer le bouton d’envoi jusqu’à sa résolution ou l’abandon par l’infrastructure. Le cache IA dépend de tokens de recherche qui retirent notamment `هل` et `أفضل`, pas de la question complète; des intentions différentes peuvent donc partager une réponse. Il ne dépend pas non plus de la version du catalogue : une correction peut rester invisible jusqu’à six heures dans une réponse déjà en cache.

**Proposition :** timeouts par fournisseur et budget global, retour progressif vers la recherche locale; clé de cache liée à l’intention conservée et à une version de données, ou mise en cache de candidats plutôt que de la réponse finale. Ne pas mettre en cache longtemps le repli résultant d’une panne IA. Le rendu déterministe actuel des éditions et la restriction aux identifiants candidats sont de bons points à conserver.

### 13. P2 — Accessibilité des modales et actions des cartes

**Code :** `index.html:1532`, `index.html:2054`; comparaison `src/components/AnimatedModalWrapper.tsx`.

Les rôles de dialogue existent, mais le site public ne gère pas de piège de focus ni d’Échap global pour les modales. Des `span role="button"` cliquables n’ont ni tabulation ni activation clavier dédiée. Les dialogues imbriqués gèrent le scroll de plusieurs façons différentes.

**Proposition :** composant/contrôleur commun : focus initial, Tab contenu dans la modale supérieure, Échap, retour au déclencheur, titre accessible et gestion centralisée du scroll. Remplacer les actions en span par des boutons.

**Inspiration :** pile de modales, gestion clavier et restitution du focus de `AnimatedModalWrapper.tsx`; cohérence visuelle header/footer de Maktabati. Vérification mobile et clavier nécessaire après implémentation.

### 14. P2/P3 — Maintenance, tests et référencement

Le site et l’admin combinent beaucoup de CSS et JavaScript inline. Tabaat n’a pas de pipeline de tests visible ni de lockfile pour le bot dans l’arborescence examinée. Le README du bot ne décrit plus exactement la sélection IA et le rendu déterministe actuels; plusieurs commentaires mentionnent encore un rate-limit KV alors que le binding natif est configuré.

**Proposition :** extraire progressivement `catalog`, `search`, `render`, `storage`, `admin-sync`, `modal`; schéma JSON et types partagés; tests Node ciblés et validation automatique avant publication. Documenter les secrets requis, contrats et modes dégradés. Charger html2canvas seulement au premier partage, après vérification du gain réel.

Pour le référencement des fiches : des pages statiques par livre, avec titre, description et données structurées, permettraient un contenu directement disponible sans exécuter l’application. Conserver les liens `?book=` existants via une compatibilité. Le site possède déjà canonical et métadonnées générales : compléter plutôt que repartir de zéro.

## Reproduire les vérifications locales

Depuis la racine du dépôt :

```sh
node docs/audit/checks.cjs
node docs/audit/sw-checks.cjs
```

Ces scripts ne contactent pas les services externes et ne changent pas le catalogue. Les logs d’erreur sur le chat sont attendus dans les scénarios de panne simulée. Les assertions servent à confirmer le diagnostic actuel; elles devront être transformées en attentes corrigées lors des correctifs.
